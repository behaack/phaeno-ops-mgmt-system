## Rollback and failure handling

| Failure point | Required action |
| --- | --- |
| Preparation/CI/rehearsal/staging fails | Leave the current API/frontend/database active; no migration or promotion. Repair the candidate and repeat affected qualification |
| Fence/backup verification fails before migration begins | Keep the release unactivated. Restore the existing runtime only after verifying no migration began, the original database/files are unchanged and writers can resume safely |
| Migration begins, fails or times out | Keep writers contained. Read actual schema/history/transaction outcome; either migration may have committed independently. Never blindly rerun, downgrade or restart the old model. Prefer a preserving forward repair; retain failed-state evidence |
| Both migrations succeed; paired API/UI acceptance fails before new writes | Retain additive schema/data. Rehearsed old API/frontend may be restored only with mutation blocked, so old writers cannot bypass custody rules or discard extended JSON. To resume the old workflow, require proof of no post-snapshot activity and a separately approved coordinated database/file recovery or reviewed preserving repair |
| Failure after writers reopen | Immediately contain affected writers; capture a fresh incident database/file/runtime recovery point and every new event/snapshot/report/file. Prefer a preserving forward fix. Do not restore the pre-release backup over newer activity or let an old writer resave new evidence. Use the old frontend only for verified compatible reads while writes remain blocked |
| Genuine database/file recovery required | Restore into new isolated targets first; prove schema, every record/file and identity/lineage integrity, reconcile all post-checkpoint changes, then obtain explicit cutover/restore authorization. Keep originals and incident copies; do not overwrite the live database in place |

`FreezeLabIngredientWithdrawalEvidence.Down` deliberately throws to protect indefinite evidence retention. `AddLabPhysicalLifecycle.Down` would drop custody/storage/review tables and fields. **Neither Down migration is an operational rollback.** The current deployment script deliberately disables automatic image rollback once migration execution begins, even if the migration command fails. An operator must follow the preserving decisions above; a previous image is not an automatic recovery plan.

Before writers reopen, the coherent final checkpoint can provide zero loss relative to that verified boundary. After reopen, the pre-release checkpoint cannot provide zero loss of new activity. Record measured restore/containment durations; no recovery-time or recovery-point guarantee is established by this planning document.
