# Post-reset Portal workflow release

## Scope and target

The owner requested the accumulated Transportation kit, sample preparation, Customer order, CRM, and delivery-target changes to be documented, tested, committed, pushed, and deployed. EF migrations are authorized. Do not repair or convert hosted business data for this release. This plan governs the production-hosted **test** Portal API and UI after the [September 29 clean cutover](HOSTED-CLEAN-DATABASE-20260929-PLAN.md). The target is the Portal PostgreSQL 18.6 database **phaeno_portal_green**, API at **api.phaenobiotech.com**, and UI at **portal.phaenobiotech.com**. Emmaus/OCIA, the public Website frontend, external Clerk identities, and automatic deployment controls remain outside scope.

The current hosted baseline is source **04e2b9a785c0b29453f067dd031b627548260693** with the clean baseline and kit label migration. The proposed source must be a single tested commit. Preserve all current hosted rows and private files; there is no reset or hosted data patch in this release. The additional EF migrations create sample/tube pair and selected-kit records, kit-finish facts, sample amount bounds, and quote delivery targets. Review the exact migration SQL before applying. Existing placed Jobs keep accepted terms, and existing records without the new amount bounds or quote target require explicit configuration or a new quote revision at the point of use.

## Preparation and release gates

1. Finish the Customer, Partner, and Phaeno guides and owning plans; regenerate the documentation catalog and corpus. Review the shared worktree for unrelated changes and freeze the exact source commit.
2. Run the complete Release backend suite against a freshly migrated disposable PostgreSQL reference database, the complete frontend unit, lint, typecheck, build, documentation, and desktop/mobile Playwright suites. Correct failures and rerun each failed gate. Manual physical scanner and scientific acceptance remain separate from automation.
3. Record the active API image, runtime configuration and file mounts, current migration history, active Vercel deployment, database size and table counts. Take a **fresh coordinated encrypted database and private-file backup**, verify a disposable restore and checksums, and retain an off-server copy. The prior reset backup is recovery history, not a substitute for this release's backup.
4. Build the API image and Portal UI from the same reviewed commit. Stage the UI without promoting it. Confirm production runtime options and deployment targets. Rehearse the idempotent migration script against a clean baseline clone and verify every hosted backup's disposable restore receipt before the live migration. The current hosted database was newly reset to that baseline; inspect its migration history and backup inventory for drift before cutover. The migrations must remain additive and complete without data repair.

## Controlled activation and rollback

The protected backup and `Deploy Portal Green` GitHub workflows are currently disabled. For this reviewed release, enable each only for its exact manual dispatch from the tested commit, verify the run, and disable it again immediately afterward. The backup workflow must complete its encrypted off-server collection and restore receipt before the deployment dispatch. The Vercel Git deployment hold remains enabled. Take the Portal deployment lock, stop only the Portal API/workers, capture a final backup under the write freeze, apply the reviewed EF migrations to the Portal database, install the matching API image, and verify health and authorized read paths. Promote the matching staged Portal UI only after the API is ready. Record exact source SHA, image ID, migration history, Vercel deployment ID, backups, restore receipts and smoke checks.

If migration or startup fails before writes reopen, restore the verified database backup, prior API image/runtime files and prior Vercel deployment as one matched set. If writes have reopened, preserve new records and assess a recovery path before rollback. Never run the old API against the new schema. Keep the retained pre-reset database and recovery packages until separate cleanup authorization.
