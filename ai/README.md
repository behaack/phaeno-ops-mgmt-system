# AI context map

Use the smallest context set that covers the task.

| Task | Read first |
| --- | --- |
| Any code change | `AGENTS.md`, then the task-specific context below |
| Account, invitation, or access change | `docs/architecture.md`, `docs/business-rules.md`, `docs/plans/AUTH-USER-SYSTEM-PLAN.md` |
| Backend endpoint or persistence change | `README.md`, matching `backend/app/Features` code, API infrastructure, and backend test plan |
| Frontend route or workflow | matching route and feature code, frontend test plan, and `ai/prompts/cross-stack-change.md` |
| UI/UX, list, record detail, form, modal, feedback, responsive, i18n, privacy, or accessibility behavior | `docs/ui-ux-principles.md`, matching frontend code, and the relevant frontend/E2E plan |
| Public company Website page, content, navigation, metadata, SEO, sitemap/RSS, responsive behavior, or visual design | `website/AGENTS.md`, `website/README.md`, `website/src/styles/design-system.css`, and the matching `website/src` code |
| Public Website localization, locale routing, language detection/selection, translated content, localized metadata, RTL, or locale-aware Website search | `docs/plans/WEBSITE-I18N-PLAN.md`, `docs/ui-ux-principles.md`, `website/AGENTS.md`, `website/README.md`, matching `website/src` code, and `backend/app/Features/Website` for search |
| First-party Website white papers, PDF-backed publication metadata, internal PDF-assisted search, or external publication indexing | `docs/plans/PUBLICATION-SEARCH-INDEXING-PLAN.md`, `docs/plans/WEBSITE-API-CONSOLIDATION-PLAN.md`, `website/AGENTS.md`, the matching `website/src` code, and `backend/app/Features/Website` |
| User-facing behavior or in-portal help | `docs/user-documentation.md`, the affected audience guides in `frontend/src/content/docs/`, matching feature code, and the relevant test plan |
| File management, orders, sample shipping, or provisioning | the corresponding `docs/plans/` file and current feature code; use `docs/plans/SAMPLE-SHIPPING-AND-INTAKE-PLAN.md` for the shared implementation and `docs/sample-shipping-operational-content.md` for the inactive first-destination candidate and activation checklist; provisioning, the order-management initial release, the shared shipping configuration/kit/tube/crosswalk/packet/intake foundation, versioned released-deliverable retention configuration, and completion-aware file/package download evidence are implemented, while warning/grace/cutoff/deletion execution, Trial Project/freebie parent issuance, physical validation, and production activation remain tracked in their owning plans |
| Public Website API, contact/order inquiries, reCAPTCHA, Website search/crawler, Mailgun, public documents, or Website data cutover | `docs/plans/WEBSITE-API-CONSOLIDATION-PLAN.md`, `docs/operations-readiness.md`, `backend/app/Features/Website`, the shared persistence code, and the consumers under `website/`; Portal owns the live public API, and the plan records the completed cutover and retirement history |
| CRM, HubSpot, prospect onboarding, service entitlement, direct/custom sale, relationship change, or offboarding | `docs/plans/CRM-PLAN.md` and `docs/plans/STANDALONE-COMMERCIAL-LIFECYCLE-PLAN.md`, then the affected account, Trial Project, order, or provisioning plan; POMS is standalone-first and the full first-party CRM core is implemented locally. Connected communications, marketing, service-case expansion, deeper operational projections, and governance extensions remain separately phased. `docs/crm-integration-strategy.md`, `docs/plans/HUBSPOT-PORTAL-LIFECYCLE-PLAN.md`, and `integrations/hubspot/` are deferred future-adapter references, and the HubSpot runtime integration is not implemented |
| Lab Operations, accessioning, sample-shipment intake, protocols, reagent preparation, library preparation, NGS send-out, solution/schema restructuring, migration reset, provider contract, or future LIMS replacement | `docs/plans/LAB-OPERATIONS-PLAN.md`, `docs/plans/LAB-OPERATIONS-INVENTORY.md`, `docs/plans/LAB-OPERATIONS-CONTRACT.md`, `docs/plans/SAMPLE-SHIPPING-AND-INTAKE-PLAN.md`, `docs/plans/PSEQ-OPERATIONS-MIGRATION-PLAN.md`, `docs/lims-integration-strategy.md`, `docs/plans/ORDER-MANAGEMENT-PLAN.md`, and current Lab Operations and Order Management code; the approved internal application scope is feature-complete, including the `phaeno_ops` reset, Commercial/Laboratory schema separation, provider contract, full operator workflow, durable customer-safe projection delivery, current-order connection, user guides, and local migrations. The pre-receipt sample-shipping configuration, return-kit and registered-tube inventory, external tube crosswalk, printable packet, packet-plus-tube scan handoff, Lab supplier-barcode adoption, and shared controller/PostgreSQL reference journey are implemented; Trial Project/freebie parent issuance remains a later phase. Validation and production activation are incomplete: hosted authenticated parent-workflow execution, representative tube/shipper/label/scanner validation, external NGS operating details, deployment, and pipeline/file ownership remain explicit gates. |
| Verification or handoff | `ai/playbooks/verification.md` and the relevant living test plan |
| Runtime configuration, deployment boundary, integration recovery, or production readiness | `docs/operations-readiness.md`, `docs/architecture.md`, and the owning feature plan |

For every major-record workflow, treat the standard list -> create/view/edit -> return flow in `docs/ui-ux-principles.md` as application-wide policy. Check the list, detail route, modal behavior, and focus/list-state restoration together rather than reviewing any one screen in isolation.

Durable facts belong in `docs/`. Active implementation state belongs in `docs/plans/`. Temporary investigation notes should remain outside the durable docs unless they produce a confirmed decision.
