# Scientific approval and release readiness

Open **Lab operations → Results & review**, then select a job to inspect its scientific review. Jobs may appear before their evidence is complete; appearing here does not establish approval or release readiness.

Scientific approval is the final Lab Ops decision. It confirms that the authorized laboratory work satisfied the configured execution and exception gates. It is not a Customer file publication action.

## Enter scientific review

Move work into **Scientific review** only after required receipt, accession, executions, QC, libraries, batches, and sendout facts are complete for the approved release scope. Confirm that every assigned execution is completed or explicitly abandoned, every blocking exception is resolved, and the registered final-result package has every expected checksummed, malware-clean artifact.

The Scientific Reviewer should be able to trace the submitted specimen through containers, material lots, equipment, protocol versions, captured results, library preparation, batches, and provider custody as applicable.

POMS checks the recorded chain from the result through its analysis inputs, sequencing output, library and successful processing attempt to the exact source tube. Every result file must identify which content belongs to that sample and analysis. Missing or conflicting links block review and release; notes cannot substitute for those links. Have the producing team register or correct the evidence before retrying.

Older results remain available, but missing historical links are not guessed or filled from the most recent attempt. A replacement preserves the original package and records its correction reason. Recorded lineage identifies the producing material; it does not by itself establish scientific validity.

## Scientific evidence requirements

The producing team can record the required information from the specimen's **Sample history**, using **Record sequencing output** and **Record analysis run**. Both staff and pipeline registration pin the current scientific requirements on new analyses. File and run names open the detailed evidence; corrections and reanalysis preserve the preceding record. Reviewers retain read access without receiving capture authority.

Scientific evidence requirements apply before new approvals and releases, including work already in progress. **Sample history** shows each analysis's saved requirement assessment. The producing team must record sequencing QC and run times, analysis software versions, settings checksum, reference versions, exact input roles/checksums and result attribution. QC needs a summary with named metrics or a referenced QC report. A meaningful **Not applicable** requires an explanation and is available only for QC, software, settings or references. It cannot waive the source tube, sample/run identity, times or file attribution.

Missing evidence or pending performer/time review blocks approval and release. A rejected on-behalf entry remains unverified until corrected and independently approved. Review those proposals under **Performer and time reviews**. Recorded coverage still requires your scientific judgment. Historical analyses without a saved requirements profile remain readable; their evidence is not invented or automatically backfilled. Capture the required evidence and create an attributed replacement before approving or releasing an incomplete older result.

## Upload scientific files

In **Record sequencing output**, select the sequencing file under **File and sample mapping**. POMS uploads and scans the actual file, verifies the stored bytes, and records its fingerprint, size and immutable file identity automatically. Continue selecting the library, submission, purchased run and exact sample/index/lane mapping that produced the file.

Use **Add document** for QC reports and other supporting evidence. Specify what the document represents, then select its file. For analysis settings, upload the configuration file actually used. Software and reference names and versions still describe the scientific process; they are not inferred from file contents.

The picker shows the configured maximum size. Wait for uploading, verification and scanning to finish before saving evidence. A rejected upload leaves the previous selection unchanged. Files larger than the limit require an approved larger-file import workflow; entering an external reference is not a substitute in this form.

Open the saved scientific record to download its managed files. POMS checks their saved fingerprint and size before returning bytes. Corrections preserve the original record and file; upload a replacement when the file changes. Uploaded files are retained as internal evidence, including uploads made before cancelling an unsaved evidence form, independently of Customer download expiry.

Historical references remain visible and are explicitly labelled **Not stored in POMS**. They are not automatically imported or verified. Upload the original file when recording an attributed correction. A retained historical settings fingerprint also does not establish file custody.

## Record the approval

Choose **Record scientific approval**, then select the complete output package by Customer sample, version, and file count. Review its file names and manifest checksum. POMS uses the service workflow for the release definition and records the reviewer and approval time. Enter an optional Customer-visible QC summary using ordinary text. Approval pins that immutable package; it does not upload or alter artifacts.

If several sample packages are ready, approve each package separately. Previously approved packages remain pinned while later packages undergo their own review. When no complete, checksummed, malware-clean package is available, the approval action remains blocked.

The reviewer must be different from every actor who recorded receipt, accessioning, execution, QC, library, batch, or sendout work in scope. A protocol author cannot approve or activate that protocol version. If either actor-separation or scientific gates fail, leave the work in review and create the appropriate exception or rework action.

## Publish readiness

Approval moves the Lab work order to **Ready for release** and publishes the controlled Customer-safe milestone to Commercial. Commercial may receive the milestone, schedule health, expected timing, and safe QC projection defined by the contract.

## Respect the release boundary

Ready for release automatically creates the Commercial release candidate for the approved package. It does not publish the result. A Result Release Manager still controls Customer visibility, and payment/credit facts never gate PSeq release.

If the Lab-to-Commercial event fails, retry the existing durable projection. Do not duplicate the approval, recreate the work order, or manually mark the Customer file released.

## Review the Customer release

A Result Release Manager opens **Order operations** > **Result release**, chooses the recognizable job and sample, and reviews the package detail before confirming publication. The detail joins scientific approval, file evidence, and release state. File administrators also see the retention receipt and preservation controls there; those permissions do not grant release authority.
