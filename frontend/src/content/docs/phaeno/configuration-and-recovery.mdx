# Configuration and file retention

Open the user dropdown menu, then choose **Administration → Order settings**.

**Order settings** controls the active scientific, Partner, commercial, release, and integration rules used by new work. Changes must be audited and should not rewrite immutable order snapshots.

The separate **File retention policies** page, after **Order settings**, **Lab settings**, **CRM settings**, and **Samples & shipping settings** in the user menu, controls the retention policy used by future released result and output packages. Only a Phaeno platform administrator can change these settings.

Use the far-left **Order settings** sidebar to move among **Quote & workflow**, **Service catalog**, **Analyses**, **PSeq kits**, **Assembly**, and **Legacy links**. Scientific service definitions are managed inside their catalog item. On wider screens the sidebar can remain pinned; when it is unpinned or the screen is narrow, open the same non-modal navigation from the edge tab. The selected subject appears in the main pane without duplicating the navigation above the configuration form.

## Maintain commercial configuration

Maintain billable items under **Service catalog**. Open an item's name and select **Edit item** (under **Actions** when deletion is also shown). Active items are available for new pricing; existing orders retain their saved details. Inactive is an ordinary catalog state. Review the name, description, base price and currency before saving.

Use **Add item** and choose **Service family**. **PSeq Lab Service** groups specific laboratory offerings, each with its own name, price, status and scientific definition. This family uses **Per sample-sequencing run**. **Other** items can use **Per kit**, **Per item**, **Per service**, or another supported unit. New items start inactive and receive automatic permanent references. References remain unchanged when items are renamed and appear under **Reference details**. A family cannot change once saved work or configuration references the item; create a new item for a different family.

One active offering in **PSeq Lab Service** clears the shared catalog-readiness requirement. Other offerings, including an older generic service, may remain inactive. Company/Department permission is separate. Configured purchases also require the selected offering's approved scientific and sample configuration. Quotes select the actual offering; additional-sample quotes retain the accepted Job's service.

To remove an unused item, open it and choose **Actions → Delete item**. Review the named confirmation, then select **Delete item** or **Cancel**. Deletion requires an inactive item whose complete history confirms it has never been active, with no saved work or configuration references. Previously active items must be retained, even after deactivation. Missing history also prevents deletion. The audit history remains after deletion.

Configure Partner PSeq Kit availability, negotiated bundle price, currency, effective period, whole-unit quantity rules and shipping restrictions. Bind each active Kit offering to an active, validated included Assembly profile. Each unit creates one included case at purchase; existing orders keep their frozen profile and outputs. Overlapping active price periods for the same Partner and item are not allowed.

Historical credit and accounting links are retained under **Legacy links**. Partner Assembly payment gates remain in its owning workflow. PSeq Customer result release depends on scientific approval and the Result Release Manager; invoice balance and credit do not gate it. Customer billing, tax, invoices and cash are maintained in **Order Ops → Finance**.

Open **Quote & workflow → Edit settings** to maintain quote validity and review the supported sample and result workflows. The initial quote validity is 30 days, and an issued quote snapshots its own expiration. The supported sample workflow uses an exact roster after quote acceptance; the supported result destination is governed Portal delivery. Free-form configuration text no longer establishes readiness. Review and save older workflow settings once, then maintain shared definitions in **Samples & shipping settings → Sample types** and destinations and rules in **Samples & shipping settings**. Each order and shipment still checks its specific requirements.

## Maintain a service's scientific definition

In **Service catalog**, open an item in the **PSeq Lab Service** family and review **Scientific definition** beneath the commercial details. This defines the included analyses, supported sample-type revisions, biological sources, outputs, published minimum and maximum turnaround, availability dates, and active state. The price comes from the parent catalog item. Use **Add definition** when none exists; otherwise use a version's **Actions → Create new version**. New definitions and versions start inactive. Activate only approved, complete definitions. Synthetic definitions cannot be purchased.

Select the supported sample types. New shipment preparation and service availability follow their latest active, effective revisions; existing commitments retain the sample identity and accepted commercial terms. **Samples & shipping settings → Sample types** maintains reusable definitions; a globally active type or matching shipping rule does not automatically make it supported by a service. Materials follow the selected types. Current configured PSeq ordering requires exactly one supported extracted-RNA tube type; assigning other types does not enable a new intake workflow. Kit and Assembly configuration remain in their own settings pages.

Each item has one current scientific definition, with prior versions retained. A scientific version cannot move to another catalog item. **Actions → Edit availability** changes when an existing version can be selected. Publishing a new active version closes overlapping prior availability for that item; editing availability cannot introduce an overlap.

Older definitions without explicit sample assignments show **Review required** and cannot be selected for new configured orders. Create a new version, review the supported sample types, and activate the approved definition. Existing accepted orders retain their saved version, scope, price, tax, and shipment instructions. New configured commitments also freeze supported sample-type revision IDs. If that revision becomes unavailable before a new shipment is authorized, staff must review the shipping configuration; POMS will not silently substitute an unrelated type. Legacy and manually quoted commitments keep their existing shipping checks.

After a concurrent configuration change, a failed save retains your edits and refreshes saved values where available. Review the latest terms before retrying. Closing an editor with unsaved changes asks whether to discard them.

## Maintain scientific configuration

Analysis definitions describe required Customer sample fields, instructions, expected outputs, and linked quoteable items. Assembly profiles describe Partner metadata, allowed files, validation, expected output contract, availability, and linked quoteable items.

Deactivate configuration that must not be used for new work. Existing orders keep their accepted definitions, profile versions, prices, currency, and commercial snapshots.

## Maintain sample-shipping configuration

The ship-to destinations in this configuration are laboratory receiving locations for samples sent to Phaeno. Customer delivery addresses for outbound kits are maintained separately under the Customer's **Departments → Delivery locations**. Confirmed kit orders retain their saved address even when a delivery-location record changes later.

Open **Administration → Samples & shipping settings**, after **CRM settings** in the user dropdown menu. Its sidebar opens separate pages for **Sample types**, **Ship-to destinations**, **Shipping procedures**, **Shipping assignments**, **Container sizes**, and **Order submission guidance**. List titles, descriptions, create actions, and available filters sit in shaded headers. The settings maintain these controlled record sets:

- ship-to destinations with the full address, receiving team, receiving hours and time zone, closure guidance, delivery directions, and carrier restrictions;
- sample types with material, quantity, primary-container, preservation, customer-label, prohibited-identifier, safety and transit requirements;
- reusable **Shipping procedures** with common packing, transit, carrier, dispatch, required-document, exception and optional customs steps;
- **Shipping assignments** linking a sample type and exact destination revision to an approved procedure revision, plus compatibility grouping and optional destination-specific additions; and
- container sizes with a fixed SKU, name, usable tube capacity and approved sample/assignment combinations. Each combination has its own temperature-control instructions and packing steps.

Follow the **Setup guide: where each instruction belongs** when configuring a new sample. Add a sample type and destination, approve the common procedure, create their shipping assignment, then configure the container combinations. Missing prerequisites link directly to the relevant screen. **Manage assignments** from a sample detail keeps that sample selected.

Create a named procedure once, review it, and mark its revision approved before selecting it in an assignment. Assignments keep that exact revision. To adopt a later procedure, create a new assignment revision and review the container combinations that use it. Existing standalone instructions remain available for reviewed conversion; the Portal does not automatically combine scientific text.

Temperature control is flexible. Specify the approved method, amount, units and preparation for each sample/container combination: regular ice, dry ice, cold packs, another method, or explicitly no cooling. Amounts can differ by container size. New procedure-based combinations require temperature-control and packing instructions before activation and packet issuance. Mixed samples must share one approved temperature-control instruction for that container; the Portal never sums amounts per sample or calculates them from tube capacity. Use separate containers if the requirements conflict. Specify the amount for one complete container, not an amount to add for every sample.


Destination codes are generated automatically when you add a ship-to destination. Enter its display name; the permanent reference is retained if you rename it or create a revision.

New records default to inactive. Activate a revision only after the address and scientific and operational instructions are approved. Selecting **Create revision** copies the current content into a new record; it does not rewrite history or any packet snapshot already issued. A new active revision replaces its predecessor when it becomes effective.

Use **Add sample type** and enter its **Name** and approved handling requirements. Its permanent reference is generated automatically; you do not enter a sample-type code. Select **Total RNA** or **Enriched RNA** under **Material type** to match the submitted material. Revisions retain previously saved material values unless you explicitly change them. The compact **Quantity** card describes submitted items. Use **Units** beneath **Submission unit** to insert **µL** or **mL** at the cursor, preserving the surrounding text. For example, insert **mL** between **20** and **tube** to make **20 mL tube**. You can also type a submission description directly. **Min** defaults to **1**; **Max** is optional. Enter positive whole-number counts, and leave Max blank for no upper limit. Max cannot be below Min. The size in “20 mL tube” describes the container; the count describes how many are submitted. The helper is limited to these two size units and contains no symbol-insertion options. Renaming a sample type in a new revision preserves the reference, and existing references are retained.

Automatic extracted-RNA intake recognizes **tube** and sized tubes such as **20 µL tube** or **1.5 mL tube** as tube counts. A volume by itself, blocks, sections and other containers do not use this workflow. Finalizing a Customer sample list still requires one eligible active sample type, its active shipping assignment and destination, and the service's supported type when assigned. Existing approved container and packing requirements still apply.

Each sample-type instruction field has a **Units and symbols** helper: primary-container, preservation, stabilizer, customer label, prohibited identifiers and safety. Earlier packaging and carrier text is retained when revising existing samples. Choose from volume, mass, concentration, length, temperature, time, percentage, centrifugation and pressure units, or scientific symbols such as **±**, **≤**, **≥** and **µ**. A selection inserts at the cursor or replaces only highlighted text, then returns focus to the instruction. Existing surrounding text is preserved.

Saving a sample-type definition does not by itself enable it for a service or change ordering and pricing. Current configured PSeq intake uses its supported registered tubes. Submission quantities describe the physical material; ordering and pricing count sample-sequencing runs.

In **Samples & shipping settings → Sample types**, open a sample type's name to see its dedicated detail page. It shows the scientific requirements, quantity and transit limits, availability and revision history. **Shipping & packing** shows current destination assignments, linked shared procedures and approved containers with their specific packing and temperature-control details. Earlier shipping text remains available for review. Copy the page address to share a link with another authorized Phaeno administrator; the link always opens that exact revision. Select a revision in the history to review it, or use **View latest revision** from an older page. **Actions → Create revision** on the latest page opens the revision editor. Saving opens the new revision's details; **Back to sample types** returns to the list.

For **Sample types**, **Ship-to destinations**, and **Shipping assignments**, use **Actions → Activate** or **Deactivate** to change availability. Confirm the selected revision; its revision number and content remain unchanged, and the status change is recorded in the audit history. **Create revision** is for changed requirements, addresses or instructions. New content revisions start inactive. An earlier active revision stays available until you activate its successor or explicitly deactivate it. When a newer draft exists, its Actions menu also offers **Deactivate revision N** for an earlier approved revision.

Activation is available on the latest revision that has not ended. A future start remains scheduled; activating a draft whose start is in the past takes effect now. Deactivation stops new use without restoring an older revision. Existing issued packets keep their recorded information.

Before activating a shipping assignment, its exact destination revision, a current sample-type revision and its selected shipping procedure must be active at activation time. The confirmation explains missing prerequisites and links to the relevant setup. For example, activate an inactive destination under **Ship-to destinations**, then return to activate the saved assignment. An ended destination requires a new assignment linked to a current destination revision. If a status change fails because another administrator changed the record, refresh the configuration and review the latest values before retrying.

The **Container sizes** list supports search and status filtering. Open a common name to review its details and revision history. Use **Add container size** or **Create revision** for bounded changes. The SKU stays fixed across revisions, including leading zeros and separators. Saving an inactive container revision creates a draft and leaves the preceding active revision available. To stop an active revision from future selection, open its detail page and choose **Actions → Deactivate revision**. Existing kits and manifests retain the container facts recorded when they were prepared.

In the size editor, select the approved sample/assignment combinations and enter each combination's temperature-control and packing instructions. Under **Kit contents**, select **Add product** for every supplied product. Choose its **Supplier**, **Product name**, and positive whole-number **Quantity** per complete kit—for example, one container and ten tubes. You can list any number of products, use several suppliers, and include any active product type. List a product once and increase its quantity for multiples. **Remove product** removes that row from the draft. Usable tube capacity is separate from these quantities.

Only active suppliers, products and product types are available for new revisions. Changing a row's supplier clears its product. Manage choices in **Lab operations → Suppliers & products**. Enable a product's **Can expire** setting when staff must record its expiration date on new inventory. Stock preparation requires a date for every flagged product in the configured contents and actual tube and shipping-container selections, regardless of product type. Saved stock retains the requirement and date recorded at preparation; changing the catalog setting does not alter that history. An active revision requires at least one product; an inactive draft may have an empty list. Earlier supplier references remain visible for older revisions, but their missing contents are not inferred. A new revision must select current catalog products. Each saved revision retains its product names, suppliers and quantities even if the catalog later changes.

**Earlier container notes** appears only when previous notes exist; review and clear text that duplicates the combination instructions. **Availability** groups the effective dates and activation setting.

Use **Preview recommendation** to enter a tube count, select the exact sample and destination assignment, and optionally enter available quantities. Blank quantities mean availability is unknown; zero excludes that size. The result favors fewer containers, then less unused capacity, and shows any unallocated tubes. A preview from a container detail page can include that draft revision. Previewing does not reserve stock, create a shipment, or estimate shipping cost.

When adding a shipping assignment, select **Sample type** by name. Beneath the selector, **Currently using revision N · Active** identifies the version used now. Inactive, ended and future-dated versions are excluded. If no revision is currently active, shipping instructions cannot be issued. Saving an inactive sample-type revision leaves the existing active revision available. When an approved successor becomes effective, rules and container compatibility follow it automatically for new shipment preparation; quantity and unit requirements are checked again at packet issuance. Already-issued packets retain their recorded sample revision and instructions. The destination remains tied to an exact revision, so a changed destination still requires a rule for that destination revision.

**Compatibility group** is a shared handling label, such as **FROZEN_RNA** for frozen RNA. Reuse a group only for sample types approved to share a shipment. Different groups cannot be combined, and **This sample type must have a separate shipment packet** prevents combination even when the groups match. Choose an existing suggestion or enter the approved label; it is not a unique generated reference.

On **Shipping assignments**, choose a rule's **Actions → Preview shared steps**. The read-only preview opens automatically for that destination and sample type, using the current time or the rule's exact start time if it starts in the future. Inactive or ended rules cannot resolve a preview. Expand **Add sample types** to check a combined shipment; the original sample type stays included. POMS displays the shared ship-to and preparation requirements. Review container-specific details through the sample's **Shipping & packing** section. An issued packet combines and freezes those details for its actual container. If a required combination rule is missing, compatibility groups differ, or a type requires its own package, POMS blocks a combined preview so the work can be corrected or split. Use **Actions → Create revision** to revise an instruction rule.

This configuration is shared infrastructure only. It does not create a Prospect Trial Project, grant a Customer promotion, place an order, or activate any real destination or sample type on its own.

Prepare and register standard kits in **Lab operations → Receipt & accession → Prepare kits** before supplying them to Customer locations. Staff choose a configured container size, record the actual tube and shipper products, register the full configured tube capacity, print the permanent container barcode, and record outbound dispatch against the delivery request. The Customer confirms arrival into location inventory and assigns each physical container to a Job during preparation. Previously prepared shipment-specific kits remain in **Kits sent**. These records retain product and lot facts, permanent tube identities, and outbound tracking. Qualify the physical tubes, container fit, seals, temperature handling, and readable barcodes before using a container size operationally.

Order submission guidance are general guidance copied to new lab orders when customer-specific instructions are not configured. Maintain them in **Samples & shipping settings → Order submission guidance → Edit instructions**. They are still required for order readiness. Existing orders keep their saved text. Use it to explain sample entry and where to find shipment instructions. Keep scientific requirements, receiving details and packing steps in their owning records instead of copying them here. Saving guidance preserves quote and workflow settings.

## Maintain released-deliverable retention

Open **Administration → File retention policies** to review or edit the global released-deliverable policy. The starting values are 30 days of standard retention, one undownloaded-package warning 5 days before the standard deadline, and a conditional 5-day grace period when any released file remains undownloaded at that deadline. Every value is a positive whole number of exact 24-hour days, and the warning lead must be shorter than standard retention.

Enter a reason for every change. A new revision applies only to packages released afterward; it never changes a deadline already communicated for an existing release. Prior revisions remain visible in policy history.

To configure a Company-specific policy, open the Customer, Partner, or Prospect in CRM **Companies**, open **Services**, select **Retention**, and add an override. Leave any value blank to inherit that value from the current global policy. The page shows the effective value and source for each field. Removing an override restores global inheritance for future releases and also requires a reason.

Retention editors retain the policy revision and inherited values shown when you opened them. A background refresh does not replace the values you are reviewing. If another administrator changes the policy before you save, the save is rejected; close the editor, reload the policy, and review the current values before editing again. Unsaved edits require confirmation before closing or leaving. While a save is underway, editing and dismissal pause. A failed save keeps your entries and shows the error in the dialog; **Retry** reloads a failed policy view.

Customer laboratory-result and Partner data-assembly output releases freeze the effective policy version and exact UTC warning, standard-deletion, and potential final-deletion times in the same transaction as release. Their authorized external detail views show the standard deadline and label the later date as conditional until grace is actually activated. Repeated payment events preserve the first release time. An older release without captured retention dates shows no automated schedule; do not infer a deadline from today's policy.

Released-file and full-package ZIP downloads retain their attempt and outcome. Only a complete successful transfer counts toward the retention condition. Partial downloads, failures, cancellations, and timeouts do not count. Older download records without verified completion remain in history and do not become successful downloads merely because the record exists.

Governed PSeq packages use the same frozen policy and verified-download rules. Downloads obey their deadline independently of cleanup, and existing schedules retain their original dates. Automated notices and physical file deletion depend on the enabled retention services. Check the receipt for their recorded outcomes; a closed download window does not prove that files were deleted.

## Accounting and recovery

Use **Order Ops → Finance** for native PSeq invoices, receipts, allocations, imports, aging and reconciliation. Export reports from the owning Finance view. An export does not record payment or mark an invoice as posted elsewhere.

Historical connector mappings and explicit QuickBooks catalog recovery remain in **Legacy links**. A queued recovery request does not prove that the connector is configured or that the catalog synchronized. An unconfigured connector reports unavailable and **Needs attention**; it records no invoice, payment, or successful balance. The active Service catalog can be maintained directly. Consult the owning integration recovery status before retrying a historical connector operation.

## Activate production dependencies

Before production use, confirm approved storage and malware scanning, notification delivery, active catalog and scientific profiles, Partner offerings and prices, applicable Partner credit decisions, quote validity, Finance responsibility, and operational ownership. Laboratory activation also requires approved bench workflows, label/printer/scanner and degraded-mode procedures, external NGS provider operating details, and approved operating procedures. Use only the equipment, destinations, and procedures authorized for real work.

## Recover a retention notice

Filter **Owned attention queues** to **Retention notices**. An urgent item identifies
the package, deadline, and notification requiring recovery. Confirm active
Organization administrators, correct the delivery issue, and retry the existing
notification. A later grace notice uses the original final date. Resolution does
not extend retention or confirm physical deletion; a persisting delivery failure
can reopen the item.

## Preserve a release or record a reissue

A Phaeno platform administrator can open **File retention policies → Review released packages**,
find the organization, and open a package's retained receipt. The detail page
shows its full manifest, checksums, original retention dates, download evidence,
cleanup outcome and reissue history. Use **Print / save PDF** for a metadata copy.
A historical release may lack captured sample lineage; do not infer missing facts.

Choose **Place hold**, select the hold type, and record the reason. **Preserve
bytes** blocks physical cleanup. **Quarantine and suspend access** also stops
current transfers and blocks new downloads; it is available only where download
monitoring is active. Neither action resets retention. Hold reasons remain in
the Phaeno management view rather than the external receipt.

Use **Release hold** with a reason when preservation is no longer needed. If the
original deadline has passed, cleanup may proceed once every hold is released
and active transfer leases have ended. A stale-record error refreshes the details
and preserves your entered reason; review the current state before retrying.

After deletion, first regenerate and approve a new package through the owning
scientific workflow. Then open the old receipt and choose **Link reissued
package**, select the eligible new release, and record the authorization reason.
POMS requires the same organization, workflow and sample where applicable, new
file objects, and a release
created after the original deletion. Linking never restores deleted bytes or
changes the original release dates.

Cleanup can remain pending for active transfers, preservation, shared source
files, an incomplete package, or provider failure. Provider failures are retried
against the same objects. **Files deleted** records successful physical cleanup;
**Downloads closed** alone does not. Escalate repeated failures with the package
reference and safe status, without copying credentials or scientific files.
