# Configuration and accounting recovery

Order configuration controls the active scientific, Partner, commercial, release, and integration rules used by new work. Changes must be audited and should not rewrite immutable order snapshots.

**File management** separately controls the retention policy used by future released result and output packages. Only a Phaeno platform administrator can change these settings.

Use the far-left **Order configuration** sidebar to move among **Defaults**, **Catalog**, **Analyses**, **Sample shipping**, **PSeq kits**, **Assembly**, and **Credit**. On wider screens the sidebar can remain pinned; when it is unpinned or the screen is narrow, open the same non-modal navigation from the edge tab. The selected subject appears in the main pane without duplicating the navigation above the configuration form.

## Maintain commercial configuration

Maintain active billable items under **Catalog**, including a permanent item code, name, description, sales unit, base price, currency, and availability. Link these Phaeno-owned items to portal analyses, Partner reagent offerings, or assembly profiles.

The designated laboratory-service item must use the permanent code `pseq-lab-service`, the sales unit `specimen`, and an active state. The catalog identifies it as **PSeq Lab Service**. POMS blocks laboratory quote issuance when this exact item is missing, inactive, or uses another unit; an unrelated specimen fee cannot replace it.

Configure Partner reagent availability, negotiated price, currency, effective period, quantity rules, and shipping restrictions for each eligible Partner. Overlapping active price periods for the same Partner and item are not allowed.

Configure Customer laboratory and Partner assembly credit separately. Approval means Net 30 release under the applicable workflow. Without credit, ready files remain on payment hold. Manual payment confirmation and release are not part of the current workflow; do not bypass that hold with an order-status change.

Set the default quote-validity period in configuration. The initial default is 30 days, and an issued quote snapshots its own expiration.

## Maintain scientific configuration

Analysis definitions describe required Customer sample fields, instructions, expected outputs, and linked quoteable items. Assembly profiles describe Partner metadata, allowed files, validation, expected output contract, availability, and linked quoteable items.

Deactivate configuration that must not be used for new work. Existing orders keep their accepted definitions, profile versions, prices, currency, and commercial snapshots.

## Maintain sample-shipping configuration

Use **Sample shipping** to maintain three controlled record sets:

- ship-to destinations with the full address, receiving team, receiving hours and time zone, closure guidance, delivery directions, and carrier restrictions;
- sample types with material, quantity, primary-container, temperature, packaging, customer-label, prohibited-identifier, safety, and transit requirements; and
- one instruction rule for an exact destination revision and sample-type revision, including compatibility grouping, packing, carrier, dispatch, delivery, required-document, exception, and optional customs instructions.

New records default to inactive. Activate a revision only after the address and scientific and operational instructions are approved. Selecting **Create revision** copies the current content into a new record and ends the prior revision when the new revision becomes effective; it does not rewrite history or any packet snapshot already issued.

Use **Instruction preview** before operational use. Select an exact destination revision, one or more sample-type revisions, and the time to evaluate. POMS displays the full resolved ship-to and detailed preparation instructions. If a required combination rule is missing, compatibility groups differ, or a type requires its own package, POMS blocks a combined preview so the work can be corrected or split.

This configuration is shared infrastructure only. It does not create a Prospect Trial Project, grant a Customer promotion, place an order, or activate any real destination or sample type on its own.

Return-kit fulfillment is operated from **Order intake**, not from configuration. The fulfillment record preserves shipper product/lot facts, the exact registered supplier-tube inventory, and outbound tracking. The current Corning vial and Therapak shipper values are pilot candidates only; activate real work only after representative tubes, shipper fit, returned volume, seal, freezing, dry-ice handling, barcode scanning, and degraded-mode procedures pass the physical validation gate.

## Maintain released-deliverable retention

Open **File management** to review or edit the global released-deliverable policy. The starting values are 30 days of standard retention, one undownloaded-package warning 5 days before the standard deadline, and a conditional 5-day grace period when any released file remains undownloaded at that deadline. Every value is a positive whole number of exact 24-hour days, and the warning lead must be shorter than standard retention.

Enter a reason for every change. A new revision applies only to packages released afterward; it never changes a deadline already communicated for an existing release. Prior revisions remain visible in policy history.

To configure a Company-specific policy, open the Customer, Partner, or Prospect in CRM **Companies**, find **Portal access and services**, select **Retention**, and add an override. Leave any value blank to inherit that value from the current global policy. The page shows the effective value and source for each field. Removing an override restores global inheritance for future releases and also requires a reason.

New Customer laboratory-result and Partner data-assembly output releases now freeze the effective policy version and exact UTC warning, standard-deletion, and potential final-deletion times in the same transaction as release. Their authorized external detail views show the standard deadline and label the later date as conditional until grace is actually activated. Repeated payment events preserve the first release time. Releases created before the snapshot migration are not backfilled and show no automated retention schedule.

Released-file and full-package ZIP downloads now create a bounded, immutable transfer attempt before storage opens. The attempt counts only after the complete server response succeeds. Partial range responses, failures, cancellations, and timeouts do not count. Abandoned started attempts are reconciled after their frozen lease expires. Existing audit rows from before completion-aware tracking are retained as non-counting `legacy_completion_unverified` failures rather than being reclassified as successful downloads.

Warning delivery, grace activation, download cutoff, and package-byte deletion remain unavailable until the released-package retention worker and production storage are activated. Completion-aware download evidence and package status are active foundations only; they do not run those later retention actions.

## Prepare manual journal entries

Open **Order operations**, then **Accounting**, to review the **Journal-entry source report**. Choose an inclusive UTC accounting-date range and download the CSV for manual entry into the accounting system. POMS creates one stable source record when a laboratory job reaches its billing boundary, an assembly output is approved, or a reagent shipment is recorded.

The report provides the stable entry ID, organization, workflow and source references, purchase-order or project reference, currency, gross amount, outstanding balance, payment status, and memo. Finance assigns general-ledger accounts, tax treatment, and posting dates outside POMS. Repeated downloads do not mark a row as posted.

QuickBooks Online integration is deferred. Do not configure OAuth, retry historical QuickBooks messages, or treat a report download as payment confirmation.

## Activate production dependencies

Before production use, confirm approved storage and malware scanning, notification delivery, active catalog and scientific profiles, Partner offerings and prices, credit decisions, quote validity, the manual accounting handoff, and operational ownership. Laboratory activation also requires approved bench workflows, label/printer/scanner and degraded-mode procedures, external NGS provider operating details, and the required database-backed verification. A successful application build alone does not prove these production dependencies are ready.
