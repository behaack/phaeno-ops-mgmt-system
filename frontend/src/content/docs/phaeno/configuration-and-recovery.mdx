# Configuration and file retention

Open the user menu, then choose **Order settings**.

**Order settings** controls the active scientific, Partner, commercial, release, and integration rules used by new work. Changes must be audited and should not rewrite immutable order snapshots.

The separate **File retention policies** page, after **Order settings**, **Lab settings**, **CRM settings**, and **Samples & shipping settings** in the user menu, controls the retention policy used by future released result and output packages. Only a Phaeno platform administrator can change these settings.

In **Samples & shipping settings → Phaeno ship-to destinations**, open an available destination's **Actions** menu and choose **Set as default**. The **Default** badge shows the current choice. Ordering is blocked without an available Default. A new Job using a customer-held kit captures that Default; when new kits are sent, staff may choose the destination at first dispatch. Later changes to the Default do not redirect an Order whose destination is fixed. A Sample type also needs an Active shared procedure and at least one usable linked Transportation kit before new Orders can proceed. Existing issued shipping inserts keep their saved destination and instructions.

Use the far-left **Order settings** sidebar to move among **Quote & workflow**, **Service catalog**, **Analyses**, **PSeq kits**, **Assembly**, and **Legacy links**. Scientific service definitions are managed inside their catalog item. On wider screens the sidebar can remain pinned; when it is unpinned or the screen is narrow, open the same non-modal navigation from the edge tab. The selected subject appears in the main pane without duplicating the navigation above the configuration form.

## Maintain commercial configuration

Maintain billable items under **Service catalog**. Open an item's name and select **Edit item** (under **Actions** when deletion is also shown). Active items are available for new pricing; existing orders retain their saved details. Inactive is an ordinary catalog state. Review the name, description, base price and currency before saving.

Use **Add item** and choose **Service family**. **PSeq Lab Service** groups specific laboratory offerings, each with its own name, price, status and scientific definition. This family uses **Per sample-sequencing run**. **Other** items can use **Per kit**, **Per item**, **Per service**, or another supported unit. New items start inactive and receive automatic permanent references. References remain unchanged when items are renamed and appear under **Reference details**. A family cannot change once saved work or configuration references the item; create a new item for a different family.

One active offering in **PSeq Lab Service** clears the shared catalog-readiness requirement. Other offerings, including an older generic service, may remain inactive. Company/Department permission is separate. Configured purchases also require the selected offering's approved scientific and sample configuration. Quotes select the actual offering; additional-sample quotes retain the accepted Job's service.

To remove an unused item, open it and choose **Actions → Delete item**. Review the named confirmation, then select **Delete item** or **Cancel**. Deletion requires an inactive item whose complete history confirms it has never been active, with no saved work or configuration references. Previously active items must be retained, even after deactivation. Missing history also prevents deletion. The audit history remains after deletion.

Configure Partner PSeq Kit availability, negotiated bundle price, currency, effective period, whole-unit quantity rules and shipping restrictions. Bind each active Kit offering to an active, validated included Assembly profile. Each unit creates one included case at purchase; existing orders keep their frozen profile and outputs. Overlapping active price periods for the same Partner and item are not allowed.

Historical credit and accounting links are retained under **Legacy links**. Partner Assembly payment gates remain in its owning workflow. PSeq Customer result release depends on scientific approval and the Result Release Manager; invoice balance and credit do not gate it. Customer billing, tax, invoices and cash are maintained in **Order Ops → Finance**.

Open **Quote & workflow → Edit settings** to maintain quote validity and review the supported sample and result workflows. The initial quote validity is 30 days, and an issued quote snapshots its own expiration. The supported sample workflow uses an exact roster after quote acceptance; the supported result destination is governed Portal delivery. Free-form configuration text no longer establishes readiness. Review and save older workflow settings once, then maintain shared definitions in **Samples & shipping settings → Sample types** and destinations and rules in **Samples & shipping settings**. Each order and shipment still checks its specific requirements.

## Maintain a service's scientific definition

In **Service catalog**, open an item in the **PSeq Lab Service** family and review **Scientific definition** beneath the commercial details. This defines the included analyses, supported sample-type revisions, biological sources, outputs, published minimum and maximum turnaround, availability dates, and active state. The price comes from the parent catalog item. Use **Add definition** when none exists; otherwise use a version's **Actions → Create new version**. New definitions and versions start inactive. Activate only approved, complete definitions. Synthetic definitions cannot be purchased.

Select the supported sample types. New shipment preparation and service availability follow their latest active, effective revisions; existing commitments retain the sample identity and accepted commercial terms. **Samples & shipping settings → Sample types** maintains reusable definitions; a globally active type or matching shipping rule does not automatically make it supported by a service. Materials follow the selected types. New PSeq orders select exactly one available Sample type, and automatic tube intake still requires a supported tube-based type and shipping configuration. Kit and Assembly configuration remain in their own settings pages.

Each item has one current scientific definition, with prior versions retained. A scientific version cannot move to another catalog item. **Actions → Edit availability** changes when an existing version can be selected. Publishing a new active version closes overlapping prior availability for that item; editing availability cannot introduce an overlap.

Older definitions without explicit sample assignments show **Review required** and cannot be selected for new configured orders. Create a new version, review the supported sample types, and activate the approved definition. Existing accepted orders retain their saved version, scope, price, tax, and shipment instructions. New configured commitments also freeze supported sample-type revision IDs. If that revision becomes unavailable before a new shipment is authorized, staff must review the shipping configuration; POMS will not silently substitute an unrelated type. Legacy and manually quoted commitments keep their existing shipping checks.

After a concurrent configuration change, a failed save retains your edits and refreshes saved values where available. Review the latest terms before retrying. Closing an editor with unsaved changes asks whether to discard them.

## Maintain scientific configuration

Analysis definitions describe required Customer sample fields, instructions, expected outputs, and linked quoteable items. Assembly profiles describe Partner metadata, allowed files, validation, expected output contract, availability, and linked quoteable items.

Deactivate configuration that must not be used for new work. Existing orders keep their accepted definitions, profile versions, prices, currency, and commercial snapshots.

## Maintain sample-shipping configuration

Open **Samples & shipping settings** to manage four records: **Sample types**, **Phaeno ship-to destinations**, **Shipping procedures**, and **Transportation kits**. Order submission guidance is maintained there as well. Customer delivery addresses for outbound kits are separate from Phaeno receiving destinations.

Start with a Shipping procedure. Choose **Add procedure** to create Draft revision 1. Save shared preparation, transit, carrier, dispatch, document, and exception steps over several edits. The Draft stays out of new Jobs until an administrator chooses **Actions → Activate**. To change a released procedure, choose **Create revision**; the successor copies the released content and can be edited without consuming another revision number. **Discard** retains the unused revision number in history. A released revision cannot be edited or reactivated after supersession or deactivation.

Add a Sample type as a Draft. Record its scientific material, quantity, primary container, preservation, labeling, identifier, safety, and transit requirements. Select its shared Shipping procedure on the Draft. The procedure choice belongs to that exact Sample type revision; changing it requires a successor Draft and activation. Activating a Sample type rechecks the selected procedure family. The Sample type and its Kit specification can be activated in either order. New Orders still need both to be ready, plus an available Default destination.

A Kit specification defines a complete kit. Enter its **Kit specification name** and stable **Kit SKU**, then choose the external **Container supplier** and purchased **Shipping Container**. The container's maximum tube capacity must accommodate the specification's usable tube count. Select a reusable named **Assembly workflow** from Lab settings; the same method may serve several kit designs.

Select the Sample type for this exact Draft, or leave it open while drafting. Required contents contain one Tube product with a quantity equal to usable tube capacity, the selected Shipping Container with quantity one, and any other required purchased products. Tube and outer-container inventory units must be **each**. Record temperature control, dry ice when needed, and effective dates. Save an incomplete Draft and finish it through **Actions → Edit Draft**. Activate once its own details and contents are complete. The Sample type may still be Draft or inactive and the assembly method may await approval. New Orders require the selected Sample type and Shipping procedure to be Active; new physical kits require an approved assembly method. A successor specification may change its name, Sample type, container, method, and contents while retaining the family SKU. Older revisions and physical kits keep their recorded facts. **Discard** closes an unused Draft while retaining its revision number.

A newer approved Transportation kit workflow can serve future assemblies without revising an otherwise compatible Active Kit specification. The workflow controls ordered Lab steps; this specification revision controls required products and quantities. Each physical kit pins the exact specification and workflow revisions, expected contents, actual component use, source lots, and scanned tube roster. Existing physical kits keep their recorded facts; use the separate withdrawal action when a particular kit must stop being used.

The Kit specifications list opens the currently usable revision and links to a pending Draft where one exists. **Back to kit specifications** from a kit detail returns to that list with its filters and page preserved; the Sample type name separately opens its own record. A **Needs attention** warning explains missing dependencies. One Sample type may have several eligible kit designs.

Each Phaeno ship-to destination has its own Draft and released revisions for address, receiving hours, time zone, closures, delivery directions, and carrier restrictions. Use **Actions → Set as default** on an available destination family. Ordering is blocked without an available Default. Changing that Default does not redirect a Job whose destination is fixed. A destination successor is prepared as a Draft and activated separately.

New Jobs require an Active Sample type, an Active revision of its selected Shipping procedure, at least one usable kit design, and an available Default destination. At placement, the Job saves its exact Sample type and Shipping procedure revisions. Later activation or ordinary deactivation does not change those pins. Ordinary deactivation stops new Jobs from selecting the affected type or procedure; an already placed Job can continue receiving packets from its saved revisions. Issued packets retain their printed destination and instructions.

When a placed Job must stop receiving further packets for a safety reason, open it in **Order Ops → Order intake** and choose **Actions → Place shipping safety hold**. Enter the reason. The hold blocks further packet issuance until an administrator uses **Actions → Resolve shipping safety hold** and records a resolution reason. Both actions appear in the Job audit timeline. Previously issued packets remain frozen. A historical placed Job without trustworthy exact revision pins requires Phaeno review before another packet can be issued; do not assign today's procedure to it by assumption.

Drafts can be edited repeatedly at the same revision number. The family allows one open Draft at a time, and a discarded number is never reused. Activate only after reviewing the effective time, changed relationships, dependency warnings, and impact on new work. Released and issued history stays linked to its exact revisions.
**Order submission guidance** is general text copied to new Orders when Customer-specific instructions are not configured. It does not replace scientific requirements, receiving directions, procedure steps, or kit packing. Existing Orders and issued packets retain their saved text.

Under **Lab operations → Transportation kits → Inventory**, choose **Prepare Phaeno kit** and select a complete Active specification with an approved assembly method. Its contents determine the purchased products. Record requested lot and expiration information, complete the ordered assembly steps and actual component use, and scan every physical tube. Verify the full packed tube roster before dispatch. Each physical kit pins its exact specification and approved workflow revisions. Qualify physical fit, seals, temperature handling, and readable labels before operational use.

## Maintain released-deliverable retention

Open **File retention policies** to review or edit the global released-deliverable policy. The starting values are 30 days of standard retention, one undownloaded-package warning 5 days before the standard deadline, and a conditional 5-day grace period when any released file remains undownloaded at that deadline. Every value is a positive whole number of exact 24-hour days, and the warning lead must be shorter than standard retention.

Enter a reason for every change. A new revision applies only to packages released afterward; it never changes a deadline already communicated for an existing release. Prior revisions remain visible in policy history.

To configure a Company-specific policy, open the Customer, Partner, or Prospect in CRM **Companies**, open **Services**, select **Retention**, and add an override. Leave any value blank to inherit that value from the current global policy. The page shows the effective value and source for each field. Removing an override restores global inheritance for future releases and also requires a reason.

Retention editors retain the policy revision and inherited values shown when you opened them. A background refresh does not replace the values you are reviewing. If another administrator changes the policy before you save, the save is rejected; close the editor, reload the policy, and review the current values before editing again. Unsaved edits require confirmation before closing or leaving. While a save is underway, editing and dismissal pause. A failed save keeps your entries and shows the error in the dialog; **Retry** reloads a failed policy view.

Customer laboratory-result and Partner data-assembly output releases freeze the effective policy version and exact UTC warning, standard-deletion, and potential final-deletion times in the same transaction as release. Their authorized external detail views show the standard deadline and label the later date as conditional until grace is actually activated. Repeated payment events preserve the first release time. An older release without captured retention dates shows no automated schedule; do not infer a deadline from today's policy.

Released-file and full-package ZIP downloads retain their attempt and outcome. Only a complete successful transfer counts toward the retention condition. Partial downloads, failures, cancellations, and timeouts do not count. Older download records without verified completion remain in history and do not become successful downloads merely because the record exists.

Governed PSeq packages use the same frozen policy and verified-download rules. Downloads obey their deadline independently of cleanup, and existing schedules retain their original dates. Automated notices and physical file deletion depend on the enabled retention services. Check the receipt for their recorded outcomes; a closed download window does not prove that files were deleted.

## Accounting and recovery

Use **Order Ops → Finance** for native PSeq invoices, receipts, allocations, imports, aging and reconciliation. Export reports from the owning Finance view. An export does not record payment or mark an invoice as posted elsewhere.

Historical connector mappings and explicit QuickBooks catalog recovery remain in **Legacy links**. A queued recovery request does not prove that the connector is configured or that the catalog synchronized. An unconfigured connector reports unavailable and **Needs attention**; it records no invoice, payment, or successful balance. The active Service catalog can be maintained directly. Consult the owning integration recovery status before retrying a historical connector operation.

## Activate production dependencies

Before production use, confirm approved storage and malware scanning, notification delivery, active catalog and scientific profiles, Partner offerings and prices, applicable Partner credit decisions, quote validity, Finance responsibility, and operational ownership. Laboratory activation also requires approved bench workflows, label/printer/scanner and degraded-mode procedures, external NGS provider operating details, and approved operating procedures. Use only the equipment, destinations, and procedures authorized for real work.

## Recover a retention notice

Filter **Owned attention queues** to **Retention notices**. An urgent item identifies
the package, deadline, and notification requiring recovery. Confirm active
Organization administrators, correct the delivery issue, and retry the existing
notification. A later grace notice uses the original final date. Resolution does
not extend retention or confirm physical deletion; a persisting delivery failure
can reopen the item.

## Preserve a release or record a reissue

A Phaeno platform administrator can open **File retention policies → Review released packages**,
find the organization, and open a package's retained receipt. The detail page
shows its full manifest, checksums, original retention dates, download evidence,
cleanup outcome and reissue history. Use **Print / save PDF** for a metadata copy.
A historical release may lack captured sample lineage; do not infer missing facts.

Choose **Place hold**, select the hold type, and record the reason. **Preserve
bytes** blocks physical cleanup. **Quarantine and suspend access** also stops
current transfers and blocks new downloads; it is available only where download
monitoring is active. Neither action resets retention. Hold reasons remain in
the Phaeno management view rather than the external receipt.

Use **Release hold** with a reason when preservation is no longer needed. If the
original deadline has passed, cleanup may proceed once every hold is released
and active transfer leases have ended. A stale-record error refreshes the details
and preserves your entered reason; review the current state before retrying.

After deletion, first regenerate and approve a new package through the owning
scientific workflow. Then open the old receipt and choose **Link reissued
package**, select the eligible new release, and record the authorization reason.
POMS requires the same organization, workflow and sample where applicable, new
file objects, and a release
created after the original deletion. Linking never restores deleted bytes or
changes the original release dates.

Cleanup can remain pending for active transfers, preservation, shared source
files, an incomplete package, or provider failure. Provider failures are retried
against the same objects. **Files deleted** records successful physical cleanup;
**Downloads closed** alone does not. Escalate repeated failures with the package
reference and safe status, without copying credentials or scientific files.
