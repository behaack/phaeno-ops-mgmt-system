# Statuses and recovery

Treat operational work, accounting source records, notifications, file scanning, and file release as separate lifecycles. Recover the failed lifecycle without rewriting accepted scope or creating duplicate records.

## Triage order operations

Use Customer lab, Partner reagent, and Partner assembly queues to find work by its current status. Prioritize:

1. scan or safety failures that block intake or release;
2. governed package, scientific-approval, or release-state conflicts;
3. missing or unexpected accounting source records;
4. Customer- or Partner-visible holds and requested corrections;
5. notifications that remain pending or failed.

The overall order status is not sufficient evidence. Check sample or shipment progress, the current quote, commercial document, scan state, release state, cancellation request, and notification record separately.

## Recover Lab projections and exceptions

Lab execution events are delivered durably to Commercial projections. If a Customer milestone, schedule, action request, or permitted QC summary is delayed, verify the Lab work order and event state, then retry the existing delivery path. Do not recreate the authorization, create a second work order, or copy Laboratory facts directly into Commercial records.

Internal and Customer-action-required exceptions are separate. Resolve the
existing blocking exception with an authorized Supervisor action and a retained
resolution note. Never copy an internal investigation description into the
Customer-safe summary. For PSeq, recover package scanning, scientific approval,
and Commercial release through their own lifecycles; payment is independent.
Partner payment holds remain separate.

## Recover PSeq accounts receivable and Partner accounting sources

PSeq invoices, receipts, allocations, adjustments, and reconciliation are native
POMS records. Retry an idempotent operation with the existing external ID or
record identifier; never create a second receipt, invoice, or reconciliation to
hide a failure. Reverse an incorrect allocation/receipt and preserve its reason.

Partner workflows continue to create stable journal-entry source rows at their
implemented billing boundaries. The report itself does not post entries or
choose general-ledger accounts.

1. Open **Order operations**, then **Accounting**.
2. Select the inclusive accounting-date range.
3. Compare the organization, workflow number, source document, reference, currency, gross amount, and balance with the operational record.
4. Download the CSV and complete account selection, tax treatment, and posting in the accounting system.
5. Preserve the stable entry ID during reconciliation; downloading the same range again does not mark a source row as posted.

QuickBooks Online integration is deferred. Historical integration messages cannot be retried, and the manual source report is not a payment-confirmation workflow.

## Recover files and releases

Files progress through **Pending**, **Scanning**, **Clean**, **Rejected**, **Failed**, or **Unavailable** scan states. Only clean files can continue to a valid release state.

- Investigate a rejected scan as a safety event; do not mark it clean manually.
- Retry a failed or unavailable scan only after the scanner or storage dependency is healthy.
- Keep output **Internal** while review is incomplete.
- Use **Ready** when operational review is complete, **Payment hold** when commercial release is blocked, and **Released** only when every applicable gate passes.
- Use **Withdrawn** when a previously available file must no longer be delivered; preserve the record and audit history.

PSeq result release is independent of credit and payment. Partner assembly keeps
its existing credit/payment hold. Do not use an order or invoice status change
to bypass either workflow's release policy.

## Recover notifications

Notification records use **Pending**, **Sending**, **Sent**, and **Failed**. Correct the delivery configuration or address, then retry the existing durable message. Confirm the final delivery state and avoid sending a separate untracked message as though it were the portal notification.

## Respect terminal and superseded states

Do not retry business actions that are rejected, declined, cancelled, withdrawn, or based on an expired or superseded quote. Start the documented replacement workflow when new scope, a new quote, or a corrected input revision is required.

For escalation, record the portal identifiers, lifecycle and visible status, safe error category, timestamps, retry count, and whether the external dependency is healthy. Keep credentials, webhook secrets, access tokens, Customer-confidential data, protected health information, and raw scientific files out of tickets and browser-bundled documentation.
